/to-grill-me Sparring: Turn-by-Turn Socratic Design Interview

The /to-grill-me Skill

A relentless Socratic sparring partner and devil's advocate. Pressure-tests assumptions, exposes failure modes, and forces concrete technical A/B trade-offs one question at a time before bad assumptions harden into technical debt.

What it does

/to-grill-me (with alias /grill-me) acts as your battle-tested Senior Principal Sparring Partner and devil's advocate. Its core mission is to actively challenge premises, force trade-offs, expose hidden failure modes, and sharpen architectural clarity before code is written.

Unlike passive LLM assistants that simply agree with whatever you type (*"the yes-man antipattern"*), /to-grill-me pushes back with rigorous mathematical discipline. It conducts turn-by-turn dialogue, presenting exactly one sharp question with concrete Option A vs. Option B choices and an opinionated engineering recommendation.

🛑 Mandatory Pushback Rule (Strictly NO CODING): If you ask /to-grill-me to write application code, implement database migrations, or run test suites, it will politely refuse. Its sole purpose is to pressure-test design decisions and trade-offs until alignment is reached.

The 6 Golden Rules of Socratic Sparring

Every sparring session follows strict cognitive-load guardrails:

  1. The 1-Question Rule (Cognitive Load Guard): Never bombards you with a massive list or 10-bullet questionnaire. Asks exactly ONE sharp, high-leverage question per turn.
  2. Do the Heavy Lifting (Concrete A/B Trade-offs): Never asks lazy open-ended questions (*"What database should we use?"*). Formulates 2–3 concrete, technically grounded options derived from codebase reality.
  3. The Opinionated Senior Recommendation: For every question presented, explicitly declares: "I recommend (Option A) because..." based on Clean Architecture, SOLID, and blast-radius control.
  4. Proactive Codebase Reconnaissance: Inspects repository files, existing models, APIs, and docs/ARCHITECTURE.md first. Never asks questions that existing code already answers.
  5. Challenge Fuzzy Language: Counters unmeasurable adjectives (*"fast"*, *"scalable"*, *"user-friendly"*) with quantitative SLAs (*"< 150ms p95 latency for 50KB payload"*), memory ceilings, or strict state enums.
  6. Anti-Bailout & Decisive Closure: If you say *"I'm not sure"*, it does not stall. It explains the real-world consequence of each alternative and recommends the pragmatic default to keep momentum.

Practical dialogue walkthrough

TURN 1: SPARRING ON FAILURE DOMAIN

Agent: "In docs/spec/checkout-spec.md, payment gateway communication currently assumes a synchronous 200 OK. What happens when the payment provider times out after 4.5 seconds or returns HTTP 504?"

  • [Option A]: Webhook with Idempotency Key (Asynchronous Settlement) — Mark order as PENDING_PAYMENT, release thread, and reconcile via signed webhook event with redis idempotency lock.
  • [Option B]: Blocking Retry Loop with Exponential Backoff — Keep the user waiting on a loader for up to 15 seconds with 3 retries.

Agent Recommendation: "I recommend Option A because Option B locks HTTP worker threads under high load and causes duplicate charges if the client refreshes. Which approach aligns with your SLA?"

Common questions

Can I invoke /to-grill-me without any existing documents?

Yes! Running /to-grill-me [idea] activates Lens 1 (Greenfield Ideation). It challenges your premise, explores whether code is even needed, and sharpens your problem framing before you author a PRD or Spec.

Why does /to-grill-me refuse to write application code?

Premature coding on unaligned assumptions is the #1 cause of software failure and AI hallucinated architecture. Socratic sparring requires an adversarial, objective mindset. Once decisions are logged, hand off to /to-spec, /to-plan, or /to-code to implement.

What is the difference between /to-grill-me and /to-clarify?

Think of /to-grill-me as the interactive sparring partner you talk to in order to debate difficult trade-offs and explore options. Think of /to-clarify as the formal quality inspector with a clipboard that scores your written document (0–100) before passing the planning gate.

It's working if

  • The agent asks exactly ONE question at a time and never floods you with long questionnaires.
  • Every question presents concrete technical options (Option A vs. Option B) with real-world trade-offs.
  • The agent provides an opinionated recommendation explaining why one option is superior.
  • It challenges fuzzy adjectives ("fast", "scalable") and forces quantifiable bounds.
  • At session end, it produces a clear Alignment Log summarizing all resolved trade-offs.

Where it fits

to-grill-me is the interactive sparring partner across the entire Pólya SDLC pipeline:
