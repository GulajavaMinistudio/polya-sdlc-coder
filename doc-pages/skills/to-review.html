/to-review Phase 4: Looking Back

The /to-review Skill

Conducts an unsparing post-implementation audit across the 5 SOLID principles, boundary specialization, mutation checks, defensive security, and release readiness.

"Fourth. Examine the solution obtained. Can you check the result? Can you check the argument? Can you derive the result differently? Can you see it at a glance? Can you use the result, or the method, for some other problem?" — George Pólya, How to Solve It (1945)
TERMINAL OR CHAT PROMPT 
/to-review @docs/spec/checkout-spec.md @docs/plan/checkout-plan.md Audit code against 5 SOLID principles, defensive security, and issue release GO/NO-GO verdict.

What it does

to-review executes Phase 4 (Looking Back) of George Pólya's heuristic framework. It performs an unsparing quality audit of completed code modifications against Robert C. Martin's 5 SOLID design principles, boundary specialization ($0, 1, \text{null}$, max payloads), and defensive security invariants (OWASP Top 10, SSRF IP allowlisting, destructive path containment, zero hardcoded secrets).

It verifies tests first through mutation experimentation, enforces the 4 Anti-Fabrication Rules (No Evidence = No PASS), inspects the git diff for cheating moves (suppressions or skipped tests), synthesizes a 30-second visual ASCII topology, answers Pólya's Two Golden Questions, and issues a definitive GO | NO-GO release verdict in docs/reviews/{slug}-review.md. It refuses to modify production code directly.

When to reach for it

Where the work currently lives decides whether this is the right skill:

The work is… Reach for
Implementation completed and green tests passed /to-review @docs/spec/{slug}-spec.md @docs/plan/{slug}-plan.md
High-risk one-way doors (auth, payments, concurrency locks, DB migrations) /to-review (mandatory adversarial doubt cycle)
A pure refactoring task claiming zero behavioral change /to-review (runs before/after diffing to prove parity)
Audit completed with defects or invariant breakages /to-fix (for First-Principles bug remediation) or /to-code
Audit approved with verdict GO, ready for public technical docs /to-docs @docs/spec/{slug}-spec.md

Prerequisites

  • Completed Implementation: Source code must be committed or staged on the active branch with tests green.
  • Upstream Specification & Plan: Target docs/spec/{slug}-spec.md and docs/plan/{slug}-plan.md must be available to evaluate conformance.
  • Runtime Evidence Mandate: Requires actual test runner output, terminal logs, or HTTP status codes. Static code reading alone can never grant a PASS.

What one run does

A single comprehensive quality review run follows eight rigorous phases:

  1. Resilience Hierarchy Priority: Evaluates code strictly in order: Correct → Safe → Holds under load → Tested → Fast → Lean.
  2. Verify the Tests First (Mutation Check): Proves test integrity by static assertion auditing or temporary worktree inversion, ensuring tests turn RED if the condition is inverted.
  3. Adversarial Doubt Cycle: Reviews with an adversarial mindset (prompted to disprove rather than validate: "Find what will break in production").
  4. Runtime Evidence Gate & 4-State Taxonomy: Evaluates every acceptance criterion across 4 states: MET ✅, SPECCED BUT MISSING 🚫, SPECCED BUT NOT APPLIED ⚠️, or BLOCKED ⚠️.
  5. The 5 SOLID Principles & Floor-Guard Diff Audit: Audits SRP, OCP, LSP, ISP, and DIP. Audits diff against cheating moves (suppressions, skipped tests, stubs).
  6. Defensive Security & Hardening: Audits against OWASP Top 10, SSRF IP allowlists, path traversal, and secrets leaks.
  7. 30-Second Visual Topology & The Two Golden Questions: Synthesizes data flow into an ASCII topology and answers: Can you use the result? Can you use the method?
  8. Release Readiness Gate: Authors docs/reviews/{slug}-review.md, issues definitive GO | NO-GO verdict, and documents timed rollback triggers.

Common questions

All unit tests passed, why did /to-review issue a NO-GO verdict?

Passing tests prove nothing if they do not assert the right boundary or were weakened. Under the 4 Anti-Fabrication Rules, any Floor-Guard violation (such as adding @ts-ignore, skipping tests, or lowering quality ratchets in config files) triggers an automatic, non-negotiable NO-GO verdict.

Why doesn't the review agent fix the production code directly?

Separation of concerns. When an auditor edits production code, it creates confirmation bias and bypasses test boundaries. The auditor documents findings using the 4-part structure (What this is → Problem → Fix → If skipped) and hands off to /to-code for surgical execution.

What is the Keep-or-Revert Gate for performance optimizations?

Any optimization whose measured benchmark impact is within noise (neutral) is flagged for deletion. Speculative complexity without measurable gain is technical debt and must be reverted.

It's working if

  • It audits test assertion strength and runs mutation checks before trusting a green test suite.
  • Every PASS / MET claim in the report cites concrete test execution or runtime evidence.
  • All reported issues follow the standardized 4-part finding structure.
  • It generates an intuitive 30-second ASCII topology diagram of the implemented system.
  • It never modifies application source code directly during the review.

Where it fits

to-review is Phase 4 in the main idea-to-ship pipeline: 

/to-explore → /to-prd → /to-spec → /to-clarify → /to-plan → 🛑 PAUSE → /to-code → 🔍 /to-review → /to-docs

It receives the completed code implementation from /to-code. If approved (Verdict: GO), it hands off directly to /to-docs for user and API documentation. If defects are found (Verdict: NO-GO), it hands off to /to-fix or /to-code.
